# 打包分发建议（VideoLingoFlow）

> 生成时间：2026-08-22
> 适用对象：需要将本项目交付给最终用户 / 团队 / 客户运维的场景

## 0. 现状盘点

| 维度 | 现状 |
|------|------|
| 形态 | 源码仓库 + `install.bat`/`install.sh`（运行时拉取 Python 3.12、Node、PyTorch、FFmpeg 等） |
| 后端 | `venv312`（Python 3.12）共享给 主后端 + QM + social 三个后端 |
| 重依赖 | PyTorch 三件套（CUDA/CPU/MPS 按平台选 wheel）、transformers/funasr/demucs/librosa/opencv、yt-dlp |
| 前端 | React + Vite，`frontend/dist` 已随仓库分发，生产模式由后端同源托管 |
| 外部二进制 | FFmpeg（系统 PATH）、CloakBrowser（thirdparty 二进制目录）、Node（可选） |
| 已有容器化 | `deploy/` 提供 `api.Dockerfile` + `docker-compose.yml`（PostgreSQL/Redis/MinIO/Nginx），面向集群部署 |
| 运行时数据 | `data/`、`control_plane_workspaces/`、`_model_cache/`（需排除出分发包） |

**核心矛盾**：项目含 2~4 GB 的 PyTorch + 模型生态，且依赖 CUDA 版本、系统 FFmpeg 等外部环境。因此**不存在"一个 .exe 搞定一切"的轻量方案**，必须按受众选择分发形态。

---

## 1. 分发形态决策树

```
目标用户是谁？
├─ 开发者 / 自有团队 / 技术运维  → 方案 A：源码 + 安装脚本（现状，推荐保持）
├─ 集群 / 多实例 / 云端          → 方案 B：Docker 镜像（生产推荐，已具备骨架）
├─ 非技术 Windows 终端用户       → 方案 C：PyInstaller 便携包（需较大改造）
└─ 需要"一键装、可离线"的团队    → 方案 D：离线依赖缓存 + 安装脚本
```

---

## 2. 方案 A：源码 + 安装脚本（现状，推荐用于技术受众）

**保持现有 `install.bat`/`install.sh` 模式**，但建议补充以下以增强可分发性：

1. **锁定依赖版本**：`backend/requirements.txt` 当前多数未 pin 版本（如 `fastapi`、`uvicorn[standard]`）。分发前应 `pip freeze > backend/requirements.lock.txt` 生成完整锁定文件，安装时优先装 lock，保证跨机器可复现。
2. **先执行上一步的瘦身结论**：卸载 7 个无引用包（`groovy py-cpuinfo semantic-version pypdfium2 orjson python-bidi safehttpx`），减少体积与 `pip check` 噪音。
3. **PyTorch 三件套单独锁**：`backend/installer.py` 已按 CUDA 选 wheel，分发时把可选 CUDA 版本列清楚（cu128/cu126/cpu），并在 README 写明"无 N 卡用户装 +cpu 版"。
4. **`.gitignore` 必须排除**：`venv312/`、`data/`、`control_plane_workspaces/`、`_model_cache/`、`*.db`、`temp/`、`frontend/node_modules/`。确认这些不在分发压缩包内。
5. **提供 SHA256 校验**：对外发压缩包附 `checksum.sha256`，避免传输损坏。

> 优点：跨平台、体积最小（不含 venv）、与现有架构契合。
> 缺点：最终用户需联网下载数 GB 依赖、需基础排障能力。

---

## 3. 方案 B：Docker 镜像（生产 / 集群推荐，已具备骨架）

当前 `deploy/api.Dockerfile` 已能构建单镜像，但仅覆盖**主后端 + 前端**。建议补齐为完整可分发包：

1. **镜像拆分**（已在 compose 中体现 API/Worker 分离，建议固化）：
   - `api` 镜像：FastAPI + 前端 dist + venv（基于 `python:3.12-slim` 或 CUDA 基础镜像 `nvidia/cuda:12.8.0-runtime`）。
   - `worker` 镜像：与 api 同源，仅 CMD 不同（`celery -A ... worker`）。
   - **QM / social 后端**：目前共用 venv、作为子进程/独立端口启动。容器化时建议要么并入 api 镜像（保持现状），要么拆为独立 service（需处理 opencv 完整版 vs headless 冲突，见下方注意）。
2. **CUDA 基础镜像**：GPU 用户用 `FROM nvidia/cuda:12.8.1-runtime-ubuntu22.04`，CPU 用户用 slim。通过构建参数 `BASE_IMAGE` 切换，避免把 CUDA wheel 塞进 CPU 镜像。
3. **多阶段构建 + 锁文件**：第一阶用 `requirements.lock.txt` 装依赖，第二阶段只拷 `site-packages`，显著减小层体积。
4. **opencv 冲突处理**：主后端要 headless、social 要完整版。容器里统一用 `opencv-python-headless`（social 的二维码/图像处理不依赖 GUI），消除 `cv2` 模块冲突与多余 GUI 系统库。
5. **模型缓存挂载**：`_model_cache/` 挂为 volume 或 MinIO，避免每次重建镜像重新下载 HF 模型。
6. **镜像体积优化**：PyTorch CUDA 镜像约 6~8 GB，属正常；可用 `pip install --no-cache-dir` + 删 `__pycache__` + 用 `dive` 检查层冗余。

> 优点：环境完全一致、一键 `docker compose up`、适合服务器/集群。
> 缺点：Windows 终端用户体验差；镜像体积大、首次拉取慢。

## 4. 方案 C：PyInstaller 便携包（面向非技术 Windows 用户，**高成本**）

若目标是"双击即用、无需 Python 环境"的 Windows 分发，可用 PyInstaller 打包 `backend/main.py` 为单目录可执行，但**本项目有显著障碍**：

1. **PyTorch 体积**：打包后单目录约 3~5 GB，启动慢，且 `--onefile` 解压耗时长，不建议用单文件模式。
2. **隐式 import（hidden-import）多**：`bs_roformer`、`funasr`、`faster_whisper`、`transformers` 大量动态/插件式导入，需手工维护 `hiddenimports` 列表（可基于之前的代码 import 扫描结果生成）。
3. **子进程调用**：`s00_platform_download.py` 用 `python -m yt_dlp` 子进程——打包后无 `python` 解释器，需改为调用 `sys.executable -m yt_dlp`，或把 yt-dlp 逻辑内联。
4. **FFmpeg / CloakBrowser 外部二进制**：需随包附带并写入 PATH 或绝对路径调用。
5. **多后端进程**：主后端 + Manager(18001) + QM + social + Redis 多进程，PyInstaller 单包难覆盖，需把 launcher（`start.bat` 的等价逻辑）也打包或用 `--collect-submodules`。
6. **建议仅打包"主后端 + 前端"**，QM/social 作为可选插件让用户另行安装，降低复杂度。

> 结论：技术可行但工作量大、收益受 PyTorch 体积限制。**仅在明确需要"零安装 Windows 体验"时投入**，否则优先方案 A/B。

---

## 5. 方案 D：离线依赖缓存（团队内网 / 受限网络）

适合不能联网拉取 PyTorch 的隔离环境：

1. 在一台同平台机器上 `pip download -r requirements.lock.txt -d offline wheels/`（含 PyTorch 对应 CUDA wheel）。
2. 把 `offline wheels/` 与安装脚本一起分发；`installer.py` 增加 `--offline` 走 `pip install --no-index -f offline wheels/`。
3. Node 依赖（`frontend/node_modules` 或预构建 `dist`）同样离线随包。
4. FFmpeg / Python 安装器也可预下载进 `offline/` 目录。

## 6. 通用建议（无论选哪种形态）

1. **先瘦身再打包**：执行上一轮报告结论，卸载 7 个无引用包；修复 `opencv` 双版本冲突（统一 headless）。
2. **`requirements.txt` 版本锁定**：生成 `requirements.lock.txt`，分发以 lock 为准。
3. **运行时数据隔离**：`data/`、`_model_cache/`、`control_plane_workspaces/`、`*.db`、`venv312/`、`temp/` 必须排除出分发物（压缩包 / 镜像层 `*.dockerignore`）。
4. **前端 dist 预构建**：生产分发用 `frontend/dist`（已随仓库），避免要求用户装 Node。
5. **配置脱敏**：`config.yaml`、`*_interfaces.json` 用 `.temp` 模板分发（安装脚本已处理），切勿把密钥入库。
6. **健康检查与冒烟测试**：打包后跑 `GET /api/health/ready` + 一次最小翻译任务，验证依赖完整。
7. **对外发版附文档**：`README`（快速开始）+ `docs/依赖清单.md`（排障）+ `deploy/README.md`（集群）+ 本文件，作为分发套件一部分。

---

## 7. 推荐落地优先级

| 优先级 | 动作 | 工作量 | 收益 |
|--------|------|--------|------|
| P0 | 执行依赖瘦身 + 统一 opencv headless + 生成 lock 文件 | 低 | 减小体积、提升可复现 |
| P0 | `.gitignore`/`.dockerignore` 排除运行时数据与 venv | 低 | 避免泄漏与体积膨胀 |
| P1 | 完善 Docker 镜像（CUDA 基础镜像切换 + 多阶段 + 模型挂载） | 中 | 生产/集群一键部署 |
| P2 | 离线依赖缓存方案（内网分发） | 中 | 受限网络可用 |
| P3 | PyInstaller Windows 便携包（仅当有明确"零安装"需求） | 高 | 非技术用户体验 |

> 总体原则：**不要尝试把 PyTorch 生态塞进一个轻量安装包**。按受众选"源码安装（技术）／Docker（生产）／离线缓存（隔离网）"三选一，便携 exe 仅作为高优先级需求时的专项投入。
